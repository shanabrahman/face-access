# Face Access

Uses one local webcam for face-based staff check-in and check-out, speaks a welcome, and records attendance on this laptop. Employee face enrollment uses uploaded photos.

## Run

Use Python 3.10 or newer. On Windows, double-click `setup.bat` to create the virtual environment, install dependencies, and start the server. Keep its window open while using the app. After setup, double-click `run.bat` whenever you want to start the app again; it opens the browser automatically. If Windows reports that OpenCV cannot start, install the Microsoft Visual C++ Redistributable (x64) from https://aka.ms/vs/17/release/vc_redist.x64.exe and try `run.bat` again.

On macOS/Linux, from the project folder:

    python -m venv .venv

Activate the environment, install dependencies, and start the local server:

    source .venv/bin/activate
    python -m pip install -r requirements.txt
    python -m uvicorn server:app --host 127.0.0.1 --port 8000

Open http://127.0.0.1:8000 and allow camera access in the browser. Keep the server bound to localhost; do not expose this development application to the internet.

## Layout

    models/    YuNet and SFace ONNX models
    staff/     local-only folders for each person's photos and/or short video
    attendance_photos/ private check-in/check-out evidence (ignored by Git)
    web/       the page served at /
    database.py SQLite employee and attendance persistence
    attendance.db generated local database (ignored by Git)
    server.py  FastAPI server

Staff photos, access logs, admin PIN data, attendance records, evidence photos, correction documents, and local settings are personal device data and must not be committed or shared. The `.gitignore` excludes these local files. When setting up from a public repository download, add staff and create an administrator PIN on each device.

The ONNX face detection and recognition models are from [OpenCV Zoo](https://github.com/opencv/opencv_zoo).

The dashboard uses database-backed attendance counts. The sidebar links to employee management, one check-in/check-out camera, attendance records, shifts, leave requests, reports, camera health, and settings. Administrators can delete all attendance records from Attendance Records after confirmation; this permanently clears attendance rows, including open check-ins, and removes linked evidence photos, but keeps employees and access/audit history. Historical attendance rows reconstructed from preserved access/audit events are hidden from Attendance Records after a clear. Attendance is recorded only after the user selects check-in or check-out and each recognized, active employee with recorded consent is confirmed across multiple frames. Multiple staff members in view are confirmed and recorded independently. The first successful check-in is preserved. A check-out followed by a later check-in is recorded as a temporary exit and return; the next check-out becomes the new final checkout. The latest checkout is treated as final unless the employee checks in again. Working hours are elapsed time from the first check-in to final checkout and include breaks. Early departures are compared with the assigned shift end and show the minutes early. Temporary exit and return timestamps and their private evidence photos are retained with the attendance record. Successful face and manual check-ins/check-outs speak only the employee's name and action; timestamps and warnings remain visual. Other entry-access events are silent. Administrators can configure each shift's start/end times, on-time window, and late cutoff; updates apply immediately, including to open attendance. For the configured 9:00 AM–5:00 PM shift, check-ins before 9:15 AM are green **PRESENT**, 9:15–9:30 AM are orange with a visible grace-period warning, and check-ins after 9:30 AM are red **LATE** with minutes late. Attendance status filters include employees who have already checked out. Administrators can disable shifts or remove them after adding an active replacement and manually reassigning employees to their intended shifts. Shifts with attendance history are archived so records remain intact but disappear from shift management. Previously disabled shifts can be re-enabled. A repeated check-in for an employee with an open check-in is shown as a green informational notice; other attendance errors remain red. Authorized administrators can configure working days, public holidays, and the timezone. Working-day and holiday settings affect the daily absence and punctuality population; approved leave is excluded. A manual attendance form is available to an administrator for employees who cannot or do not wish to use face recognition; it requires an audit reason.

Administrators can use **Ask Your Attendance Data** from the sidebar or dashboard to ask questions about live employee, attendance, shift, department, and approved-leave data. It uses a local intent classifier and parameterized SQLite queries; no external AI service, face image, or biometric embedding is used. Chat history is separated by authenticated session and can be cleared. It supports late-arrival rankings, today's department absenteeism, month-to-month attendance trends, open check-ins, and daily issue summaries. Present and checked-out employee lists include their saved check-in or check-out evidence photos when available; the images are served through the administrator-protected attendance-photo route. Attendance reports can be downloaded as CSV, Excel (`.xlsx`), or PDF. Daily absence decisions use each assigned shift's start plus grace deadline, approved leave, working days, and configured public holidays. Monthly trend comparisons use completed calendar days and recorded check-ins, not scheduled workdays. Open check-ins are excluded from completed working-hour calculations.

On first use, create a local administrator PIN (at least six characters). The PIN is stored as a salted hash in `admin.json`; protected sessions expire after 30 minutes. Keep the PIN private.

### Employee accounts

The existing HR dashboard remains the organization-wide management area. After signing in with its existing administrator PIN, open **Employee Management → Employee Account Management** to create a login for an existing employee, reset its password, activate or deactivate access, and set that employee's annual leave allowance. This creates an account keyed to the existing Employee ID; it does not create another employee profile. Passwords are stored as salted PBKDF2 hashes and are never returned by the account API.

Employees use **Employee Login** in the sidebar with their Employee ID or registered email. Employee sessions expire after 30 minutes of inactivity and are separate from the HR session. The employee portal limits profile, attendance, evidence-photo, leave, correction, and report data to the logged-in Employee ID. Employees can submit leave and attendance correction requests; HR reviews them in the existing dashboard. Approving a correction applies the requested time to the attendance record. Annual leave balances are shown only after HR configures an allowance; approved leave is counted in inclusive calendar days for the current year.

On first startup, `attendance.db` is created. Existing staff folders are assigned generated employee IDs without moving or deleting face samples. Existing CSV events are imported idempotently as access history; historical attendance check-in events remain available in Attendance Records, but if a database attendance record already exists for the same employee and date, that record is shown instead of adding duplicate legacy rows. A checkout is paired with the latest earlier unmatched check-in for that employee and date. Legacy events do not contain reliable late or early-leave calculations, so the table leaves those values blank rather than inventing them. Legacy employee profiles have no recorded biometric consent until an administrator explicitly records it. New face enrollment requires the consent checkbox. Withdrawing consent through **Delete face data** removes the employee's face samples, disables the biometric profile, and retains attendance/audit history.

After confirmed live-camera recognition across three sequential frames, check-in and check-out save the latest JPEG frame as separate attendance evidence; no head movement is required. The server confirms that the saved photo contains the recognized employee and checks that exact photo with the local passive anti-spoof model. If validation or photo saving fails, attendance is rejected. New camera records store the model's liveness score. Older records are preserved as-is, so scores saved by earlier versions are not reclassified; manual attendance without a camera photo has no liveness result. Evidence is stored separately under `attendance_photos/`, excluded from Git, and served only through administrator-authenticated endpoints; raw filesystem paths are not returned in attendance API responses or CSV exports. Administrators can preview, download, or individually delete a photo from Attendance Records. Deleting all attendance records also removes their evidence photos. Set `FACE_ACCESS_PHOTO_DIR` to change the evidence storage directory. `FACE_ACCESS_PHOTO_RETENTION_DAYS` optionally removes evidence older than the configured number of days at server startup; the default `0` keeps photos until an administrator deletes them. Existing records are preserved by the migration and show **No Photo**.

The local anti-spoof model is [MiniFASNet ONNX](https://github.com/facenox/face-antispoof-onnx/tree/2f8dd93dd0fd9d120f08e83d9020719f67ffdb68), pinned at commit `2f8dd93dd0fd9d120f08e83d9020719f67ffdb68` and stored at `models/face_antispoof_98.20.onnx`. Its SHA-256 is checked at startup; a missing, altered, or unloadable model blocks camera attendance rather than silently bypassing photo verification. The model's Apache-2.0 license is included in `licenses/FACE_ANTISPOOFING_APACHE-2.0.txt`. Passive photo classification is faster and requires no prompted motion, but does not guarantee protection against replayed video, real-time deepfakes, or other sophisticated presentation attacks. Anti-spoof accuracy should be tested under actual camera, lighting, and employee conditions; monitor false accepts and rejects before relying on these checks for high-security decisions.

Administrators can manage employee profiles, shifts, attendance, and leave requests. Enrollment rejects photos with a small, blurry, or poorly lit face. Shift times and attendance timestamps use the configured IANA timezone (Asia/Qatar by default); an end time earlier than the start time represents a shift that crosses midnight. Each shift stores an on-time window and a late cutoff; times between those thresholds are the grace period.

The dashboard lets an authenticated administrator change the PIN by verifying the current PIN and confirming a new one; existing admin sessions are signed out when the PIN changes. `entries.csv` remains the compatibility/audit log and `settings.json` keeps legacy access schedules. Employee profiles, attendance, shifts, leave requests, settings, and migrated access events are stored in the local SQLite database. These local data files are excluded from version control. Attendance report export is currently CSV.

This is a local demo, not hardened physical-access security. Face attendance uses face recognition and passive photo anti-spoofing without a movement-based live-camera challenge; replayed or manipulated video may fool it. Do not rely on face recognition as the sole safeguard for a real entry point. The app does not provide separate HR user accounts/roles or Excel/PDF report export.
